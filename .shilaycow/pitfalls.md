# Pitfalls

## 票的驗收條件沒修時不一定會失敗,或根本做不到

- 發生了什麼:兩個任務各一次。第一次:todo-api 的 T-02 把「連跑三次都是 id 1」當作修好的標準,沒修的腳本也會偶然通過(c5da171;builder 在 https://github.com/pitaya943/Shilaycow-trial/pull/3#issuecomment-7065779044 指出)。第二次:persist 的 T-02 有一項檢查在改動前就通過(長度 0 的檔案),還有一項做不到(紀錄檔要包含自己那個 commit 的雜湊);builder 在 #10 的 Ready 留言指出。
- 怎麼避免:票的驗收條件要寫成沒修時必然失敗的步驟(例如先在埠上放一個已知的服務),不要靠競態碰運氣;交出票之前,自己對現在的程式跑一次每一項檢查,看到它失敗。
- 次數:2
- Sources: #1, #8

## 簡述沒說、使用者實際會碰到的邊界沒有人決定

- 發生了什麼:due-dates 合併後,Owner 試用時發現標題再長服務也照單全收。簡述沒有規範長度;寫簡述的人沒想到,建置的人沒問,驗收的人沒列出來(https://github.com/pitaya943/Shilaycow-trial/issues/5#issuecomment-7067943648)。第二次:priority 的簡述已經有一整節 Assumptions,驗收仍找出三類沒人決定的邊界:型別不符的資料檔、唯讀的舊檔與降級時的訊息(#21),一個請求有多個錯時只回第一個(#22)。
- 怎麼避免:寫簡述時把長度、大小、數量的上限,空的與重複的輸入,同時多人,資料存多久,逐項給一個預設並寫在「假設」;驗收時試極端的輸入,沒有規範的列為 `unspecified`。
- 次數:2
- Sources: #5, #16

## 換掉實作時,邊界輸入的行為跟著底層一起變了

- 發生了什麼:把記憶體裡的 list 換成 SQLite 之後,編號 2^63 以上的「標為完成」從 404 變成 500(#9 的判定,發現 1;修正在 010f271)。同一類的還有孤立代理字元的標題(#11 的判定,發現 3)。現有的測試只用了普通的輸入,所以全部通過。
- 怎麼避免:在不變的介面後面換實作時,先寫一支送出極端輸入(極大、極小、空的、非法編碼)的腳本,對舊的與新的程式各跑一次並比對,在票送去驗收之前就做,不要等到最後的 `blast-radius`。
- 次數:1
- Sources: #8

## Ready 留言或 trail 寫了沒有實測過的行為

- 發生了什麼:priority 的 T-01 builder 在 trail 寫「唯讀的資料檔會在啟動時就被拒絕」,同時承認在 root 下沒辦法重現;驗收者以非 root 實測,只有舊四欄的唯讀檔被拒絕(https://github.com/pitaya943/Shilaycow-trial/pull/17#issuecomment-7096327358)。
- 怎麼避免:沒有實際跑過的行為,寫成「推測,未實測」並說明為什麼跑不了;能換個方式跑(例如 `setpriv --reuid=65534` 以非 root 執行)就先跑。
- 次數:1
- Sources: #16
